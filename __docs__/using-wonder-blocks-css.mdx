# Using Wonder Blocks CSS

Wonder Blocks components are styled with
[CSS Modules](https://github.com/css-modules/css-modules). Every package that
has component styles ships them as a stylesheet, and its JavaScript entry
imports that stylesheet. The ESM build (`dist/es/index.js`, which bundlers use)
imports its own copy, `dist/es/index.css`; the CommonJS build (`dist/index.js`)
imports `dist/index.css`. The two files are identical.

```js
// @khanacademy/wonder-blocks-button/dist/es/index.js
import "./index.css";
```

`wonder-blocks-core` is one of these packages, so in practice every app that
uses Wonder Blocks loads Wonder Blocks CSS. This page covers what your app
needs for that to work:

1. [A bundler that handles CSS](#bundler-setup) imported from `node_modules`.
2. [A cascade layer declaration](#layer-order) that loads before any Wonder
   Blocks CSS.
3. [An understanding of how your styles win](#cascade-contract) over Wonder
   Blocks styles.
4. [A CSS mapping in your test runner](#tests).

It also explains [what each package exports](#package-exports) and, for
contributors, [how Wonder Blocks CSS is written](#writing-css-modules-in-wonder-blocks).

Server-side rendering and other uses outside a bundler aren't covered yet.

## Bundler setup

Your bundler has to process `.css` files imported from JavaScript, including
files in `node_modules`. Without it, the build fails on the
`import "./index.css"` in each Wonder Blocks package, or the components render
unstyled.

You don't need to configure CSS Modules for Wonder Blocks. The class names
are hashed when Wonder Blocks is built, and `dist/index.css` is plain CSS.

### rspack

Add a rule for `.css` files that runs `css-loader`, followed by
`CssExtractRspackPlugin.loader` in production or `style-loader` in
development. You can also use rspack's built-in CSS support
(`experiments.css`) instead.

Don't exclude `node_modules` from the rule. This is the rule Khan Academy's
frontend uses (`getCssRule` in `libs/config/rspack/src/rspack.config.ts`):

```ts
function getCssRule(cssExtractor: string) {
    return {
        test: /\.css$/,
        use: [
            // `rspack.CssExtractRspackPlugin.loader` in production,
            // `require.resolve("style-loader")` in development.
            cssExtractor,
            {
                loader: require.resolve("css-loader"),
                options: {url: true},
            },
        ],
    };
}
```

If your app also uses `sideEffects: false` or similar tree-shaking settings,
note that every Wonder Blocks package lists `"sideEffects": ["**/*.css"]` so
the CSS import is never dropped.

### Vite

Vite processes CSS imported from JavaScript, including from `node_modules`,
without extra configuration. Wonder Blocks' own Storybook runs on Vite.

### Breakpoints in your own CSS

If you write CSS that uses Wonder Blocks breakpoints, see the Tokens package
for the `@khanacademy/wonder-blocks-tokens/custom-media.css` export. It needs
`@csstools/postcss-global-data` and `postcss-custom-media` in your PostCSS
setup. Nothing in this section is needed to load Wonder Blocks' own CSS: its
breakpoints are already expanded in `dist/index.css`.

## Layer order

Every rule in Wonder Blocks CSS is inside a
[cascade layer](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer)
called `shared`. A few element resets are in a nested layer, `shared.reset`.

Browsers order layers by the first time they see each one. Declare the order
once, in a `<style>` tag in the page `<head>`, **before any stylesheet loads**.
Otherwise the order depends on which stylesheet happens to load first, which
can change as bundles are split differently.

> **Pending [WB-2687](https://khanacademy.atlassian.net/browse/WB-2687):** the
> canonical declaration, including where `shared.reset` goes relative to
> consumer sub-layers such as `shared.base`, hasn't been decided yet. This
> section will be updated with that declaration. Until then, use the
> declaration below.

The declaration Khan Academy's frontend uses today
(`libs/dev/page-template/src/make-page.ts`), and that Perseus' Storybook
injects (`.storybook/main.ts`), is:

```html
<style>
    @layer reset, shared, shared.base, legacy;
</style>
```

- `reset`: your app's global reset or normalize styles.
- `shared`: Wonder Blocks component styles. Your app can put shared styles here
  too.
- `shared.base`: your app's base element styles.
- `legacy`: styles that must win over Wonder Blocks, layered so they still
  lose to unlayered styles.

Later layers win over earlier ones, and unlayered styles win over every layer.

## Cascade contract

Because Wonder Blocks rules are in `@layer shared`, **unlayered CSS in your app
always wins over Wonder Blocks**, whatever the specificity and in every state:
default, `:hover`, `:active` and `:focus-visible`. Aphrodite styles are
unlayered, so styles you pass to a component's `style` or `styles` prop also
win.

This is different from when Wonder Blocks used Aphrodite. Then, the component's
own state styles could win over a consumer override. Some things to know:

- **Overrides persist in every state.** If you set `color` or
  `text-decoration` on a `Link` or `Tabs` through `style`, that value now also
  applies on hover and press, where Wonder Blocks used to apply its own state
  styles. See [WB-2487](https://khanacademy.atlassian.net/browse/WB-2487).
- **Focus rings.** If you set `outline` or `box-shadow` on a focusable
  component (for example, a custom opener), your value replaces the Wonder
  Blocks focus ring while the element is focused. This is an accepted edge case:
  if you override these properties, make sure your styles still show a visible
  focus indicator.
- **Media queries.** A media query in your app that sets the same property as
  a Wonder Blocks rule (for example, a small-screen rule in `Modal`) now wins
  over Wonder Blocks, where it used to lose. Check these overrides when
  upgrading.

## Tests

Test runners like Jest and rstest don't process CSS. Map `.css` imports to a
module that does nothing, so the `import "./index.css"` in Wonder Blocks
packages doesn't fail:

```js
// jest.config.js
module.exports = {
    moduleNameMapper: {
        // Load a .js file with no exports whenever a .css file is requested.
        // `*.module.css` files in your own code still need their own mapping
        // (for example `identity-obj-proxy`).
        "(?<!\\.module)\\.css$": "<rootDir>/config/test/style-mock.js",
    },
};
```

```js
// config/test/style-mock.js
module.exports = {};
```

This is what Perseus does (`config/test/test.config.js`). Khan Academy's
frontend does the same for rstest, mapping `/\.(css|less)$/` to a style mock in
`make-rstest-config.ts`.

Mocking Wonder Blocks CSS **doesn't change rendered class names or snapshots**.
The hashed class names (for example `wb-badge-badge-cbb1e92a`) are written into
the Wonder Blocks JavaScript at build time, so components render the same class
names whether or not the CSS loads. Tests can't see the styles themselves, as
with Aphrodite in a test environment; use visual regression tests for those.

## Package exports

Packages with component styles have these exports:

| Export                                         | File                                  | Contains                                                                                                |
| ---------------------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `@khanacademy/wonder-blocks-<name>`            | `dist/index.js`, `dist/es/index.js`   | The components. Each build imports its own copy of the stylesheet for you.                              |
| `@khanacademy/wonder-blocks-<name>/css`        | `dist/es/index.css`, `dist/index.css` | The component stylesheet: the CSS Modules rules, in `@layer shared`.                                    |
| `@khanacademy/wonder-blocks-<name>/styles.css` | `dist/css/vars.css`                   | Only in packages with component tokens: the package's CSS variables (`--wb-c-<name>-*`) for each theme. |

Don't mix up the names: **`./css` is the component styles** and
**`./styles.css` is CSS variables**.

You don't normally import either one:

- The JavaScript entry already imports the component stylesheet. `./css` is a
  conditional export that resolves to the same copy (`import` →
  `dist/es/index.css`, `require` → `dist/index.css`), so importing it as well
  doesn't load the CSS twice. Import it directly only if you need the stylesheet
  without the components, for example to preload it.
- The variables in each package's `./styles.css` are also merged into
  `@khanacademy/wonder-blocks-tokens/styles.css`, which every app imports (see
  [Get Started](./?path=/docs/get-started--docs)). Import a package's
  `./styles.css` only if you can't load the full tokens stylesheet.

## Writing CSS Modules in Wonder Blocks

This section is for Wonder Blocks contributors.

- Each component's styles live in a colocated `*.module.css` file. The build
  runs `postcss.config.cjs`:
    1. `postcss-import` inlines shared styles from
       `@khanacademy/wonder-blocks-styles` (for example
       `@import "@khanacademy/wonder-blocks-styles/focus-styles.css";`).
    2. `@csstools/postcss-mixins` expands mixins such as
       `@apply --wb-focus-visible;`.
    3. `postcss-custom-media` expands the breakpoint custom media queries.
    4. A last step wraps every rule in `@layer shared`, so you don't write it.
- Use tokens (`var(--wb-…)`) instead of raw values. Stylelint enforces this
  (`pnpm lint:css`).
- Don't use `composes` or `@value`.
